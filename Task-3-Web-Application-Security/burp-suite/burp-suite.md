# Burp Suite Advanced Testing

## 1. Objective

The objective of this exercise was to use Burp Suite Community Edition to inspect HTTP traffic generated by a local Damn Vulnerable Web Application (DVWA) instance, intercept and modify a login request, and perform basic parameter fuzzing using Burp Intruder.

The exercise focused on understanding how HTTP requests are structured, how request parameters can be modified during testing, and how response status codes and lengths can be compared during automated testing.

## 2. Lab Environment

| Component | Details |
|---|---|
| Interception tool | Burp Suite Community Edition |
| Target application | Damn Vulnerable Web Application (DVWA) |
| Target URL | `http://127.0.0.1/dvwa/login.php` |
| Browser | Burp Suite built-in browser |
| Target environment | Local Kali Linux lab |
| DVWA security level | Low |
| Intruder attack type | Sniper |
| Test parameter | `username` |
| Test payloads | `admin`, `test`, `invalid` |

All testing was performed against the local lab application.

## 3. HTTP Request Interception

### Procedure

1. Started Burp Suite using a temporary project and the default configuration.
2. Opened the built-in browser from Burp Suite.
3. Navigated to the local DVWA login page.
4. Used **Proxy → Intercept** to inspect intercepted traffic.
5. Used **Proxy → HTTP history** to locate requests sent to `/dvwa/login.php`.
6. Identified a `POST` request containing the login form parameters.

The captured request included HTTP headers, cookies, and form parameters. The request body contained fields such as `username`, `password`, `Login`, and `user_token`.

### Evidence

- `../screenshots/41-burp-login-intercept.png`

**Observation:** Burp Suite allowed the login request to be inspected before it was forwarded to the target application. HTTP history also provided a record of the requests and their response status codes.

## 4. Login Request Modification

### Procedure

1. Located the `POST /dvwa/login.php` request.
2. Inspected the request body in Burp Suite.
3. Modified the username value from `admin` to `test`.
4. Forwarded the modified request.
5. Observed the resulting login page.

### Result

The application displayed **Login failed** after the modified login attempt.

### Evidence

- `../screenshots/42-burp-login-intercept-failed.png`

**Observation:** Changing a form parameter changed the input processed by the application. The failed login response demonstrated that the modified request did not authenticate successfully.

This test demonstrates request manipulation; it does not, by itself, establish that the application is vulnerable to an authentication bypass.

## 5. Intruder Parameter Fuzzing

### Objective

Burp Intruder was used to submit a small set of controlled values for the `username` parameter and compare the application's responses.

### Procedure

1. Selected the captured `POST /dvwa/login.php` request from HTTP history.
2. Sent the request to **Intruder**.
3. Selected the **Sniper** attack type.
4. Cleared the automatically selected payload positions.
5. Marked only the username value as the payload position.
6. Configured a simple payload list.
7. Started the attack and reviewed the results table.

### Payload List

| Payload | Purpose |
|---|---|
| `admin` | Test the known administrator username |
| `test` | Test a generic username |
| `invalid` | Test a deliberately invalid username |

### Observed Results

The saved Intruder results show the following:

| Payload | HTTP status code | Response length |
|---|---:|---:|
| `admin` | 302 | 481 bytes |
| `test` | 302 | 482 bytes |
| `invalid` | 302 | 481 bytes |

The screenshot also contains an initial request row with a response length of 482 bytes.

### Interpretation

All three tested payloads returned HTTP status code `302`, with response lengths between 481 and 482 bytes. A `302` status indicates a redirect response, but it does not independently prove successful authentication.

The small response-length differences are not sufficient to determine whether a username exists or whether authentication succeeded. Reliable conclusions would require inspecting the response headers, redirect destination, resulting page, and session state.

### Evidence

- `../screenshots/43-burp-intruder-results.png`

**Community Edition limitation:** Burp Intruder Community Edition uses a throttled attack engine. The test used a short payload list and was limited to the local lab.

## 6. Findings

1. Burp Proxy can intercept HTTP requests sent to a local web application.
2. HTTP history can be used to identify and review login requests.
3. Request parameters can be modified to observe application behaviour.
4. Intruder can automate testing a selected parameter with a controlled payload list.
5. HTTP status codes and response lengths are useful comparison signals, but they must be interpreted in context.
6. The modified login request failed; no authentication bypass was demonstrated by this exercise.

## 7. Security Recommendations

- **Server-side authentication:** Validate credentials on the server and ensure authentication decisions cannot be bypassed by modifying client-supplied parameters.
- **Password storage:** Store passwords using a modern password-hashing algorithm designed for passwords, such as Argon2id, bcrypt, or scrypt, with appropriate parameters and salts.
- **Transport security:** Use HTTPS to protect credentials and session cookies in transit.
- **Session protection:** Use appropriate cookie attributes, including `HttpOnly`, `Secure` when using HTTPS, and a suitable `SameSite` policy.
- **Rate limiting:** Apply reasonable rate limits and monitoring to authentication endpoints to help detect automated login attempts.
- **Error handling:** Avoid revealing unnecessary account information through authentication errors or response differences.
- **Security testing:** Review response bodies, redirects, and session behaviour rather than relying only on status codes or response lengths.

## 8. Conclusion

The exercise covered HTTP request interception, login parameter modification, and basic username parameter fuzzing with Burp Suite Community Edition against a local DVWA instance.

The modified login attempt failed, and the Intruder results showed HTTP `302` responses with lengths of 481–482 bytes for the tested payloads. These observations document the behaviour seen in the lab but do not establish an authentication bypass or username enumeration vulnerability.
